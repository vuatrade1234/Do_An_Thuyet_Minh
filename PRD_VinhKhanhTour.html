1. Tổng quan & Bối cảnh (Background & Overview)

VinhKhanh Tour là một giải pháp công nghệ toàn diện nhằm số hóa và nâng tầm trải nghiệm du lịch tại các khu ẩm thực, nhà hàng. Thay vì phụ thuộc vào hướng dẫn viên du lịch trực tiếp hoặc các bảng thông tin tĩnh truyền thống, du khách có thể chủ động khám phá qua thiết bị di động cá nhân.

Bối cảnh thực trạng (Problem Statement):

  • Khách tham quan cá nhân thường gặp khó khăn trong việc tiếp cận các thông tin chuyên sâu tại các điểm tham quan.
  • Hệ thống biển báo thông tin thiếu sự đa dạng, tạo ra rào cản ngôn ngữ đối với đa số du khách quốc tế.
  • Ban quản lý gặp nhiều rào cản trong quá trình thu thập và phân tích dữ liệu hành vi của du khách nhằm đánh giá và nâng cao chất lượng dịch vụ.

2. Mục tiêu & Chỉ số đo lường (Objectives & KPIs)

Mục tiêu Kinh doanh (Business Goals)

  • Nâng cao trải nghiệm du lịch: Cung cấp hệ thống thông tin đa ngôn ngữ kết hợp giọng nói (Audio) tự động, góp phần tối ưu sự hài lòng của du khách lên mức 80%.
  • Thấu hiểu hành vi du khách: Thu thập dữ liệu di chuyển (được ẩn danh) từ ứng dụng nhằm phục vụ cho việc tối ưu hóa lộ trình và quy hoạch không gian tham quan.
  • Tối ưu hóa chi phí vận hành: Cơ chế quản lý CMS cho phép Ban ban quản lý cập nhật nội dung theo thời gian thực mà không phụ thuộc vào việc thay thế cấu trúc biển báo vật lý.

Chỉ số Đo lường Hiệu quả (Key Success Metrics - KPIs)

  • Tỷ lệ chuyển đổi: Tối thiểu 40% khách tham quan thực hiện tải ứng dụng hoặc truy cập qua mã QR.
  • Thời gian tương tác (Session Duration): Trung bình người dùng tương tác với hệ thống và theo dõi > 60% tổng thời lượng của các Điểm Audio (POI).
  • Hiệu suất hệ thống: API phản hồi nhanh chóng (chuẩn < 200ms) và duy trì độ ổn định (Uptime) ở mức 99.9%.

3. Đối tượng & Hành trình

3.1. Chân dung Người dùng (User Personas)

🎒

Khách Tham Quan (End-User)

Nhu cầu: Có nhu cầu tìm hiểu ẩm thực và ưu tiên sự linh hoạt trong lộ trình di chuyển. Yêu cầu giao diện ứng dụng trực quan và hỗ trợ ngôn ngữ phù hợp.

Hành vi định danh: Ưu tiên phương thức tra cứu thông tin nhanh chóng qua mã QR. Thường xuyên thay đổi vị trí nên yêu cầu hệ thống hoạt động ổn định ngay cả trong điều kiện kết nối mạng hạn chế.

👨‍💼

Quản Trị Hệ Thống (Admin)

Nhu cầu: Yêu cầu hệ thống thao tác trực quan để thiết lập nội dung các tuyến Tour và Điểm tham quan (POI), quản lý thư viện đa phương tiện hiệu quả và đối soát tọa độ trên nền tảng bản đồ số.

Hành vi định danh: Thao tác chủ yếu trên giao diện máy tính nghiệp vụ, cần hệ thống báo cáo (Dashboard) chuẩn hóa và biểu đồ phân tích một cách chi tiết để báo cáo.

4. Kiến trúc Hệ thống (System Architecture)

Hệ thống được thiết kế theo mô hình Client-Server hiện đại, phân tách rõ ràng trách nhiệm giữa phân hệ quản trị nội dung (CMS) và ứng dụng dành cho khách hàng (Mobile Client).

flowchart LR subgraph client [Client Applications] mobile[Mobile App / Web App] cms[Web CMS Admin] end subgraph backend [Backend Services] t_api[.NET Core API] auth[Firebase Authentication] end subgraph db [Data Tier] fstore[(Cloud Firestore DB)] storage[(Cloud Storage Media)] end mobile --> t_api cms --> t_api cms --> auth t_api --> fstore t_api --> storage

Công nghệ triển khai:

Backend Architecture: C# .NET 8 (Web API), tích hợp Mapster và Entity Framework Core logic.

Database Tier: Cơ sở dữ liệu phi quan hệ Google Cloud Firestore giúp tối ưu tốc độ đọc theo thời gian thực; Firebase Storage để lưu trữ và phân phối nội dung Audio/Image.

Frontend Admin Services: React framework mở rộng cùng việc tích hợp chặt chẽ với Google Maps API nền tảng.

Mobile Client Services: Giao diện hiển thị người dùng xây dựng trên nền Flutter / React Native đáp ứng trên cả hai môi trường hệ điều hành chuẩn iOS và Android.

5. Yêu cầu tính năng chi tiết (Detailed Features)

🛡️

5.1 Xác thực & Phân cấp quyền truy cập

CMS cấp phát quyền truy cập bảo mật dựa trên chuẩn Firebase Auth. Đồng thời thiết lập cơ chế phân quyền (Role-Based Control) cho SuperAdmin và ContentEditor để kiểm soát luồng thao tác với dữ liệu nền tảng.

Firebase Auth JWT Bearer
📍

5.2 Quản trị thông tin Điểm tham quan (POI)

Module cung cấp giao diện tương tác trên bản đồ (GMap Web) để trích xuất tọa độ địa lý. Cho phép định cấu hình bán kính kích hoạt (Radius) và kiểm duyệt chuỗi hình ảnh, âm thanh chuẩn hóa đa ngôn ngữ.

Google Maps API File Storage Uploads
🗺️

5.3 Quản lý luồng Tuyến (Tour)

Cung cấp chức năng thiết lập mới các Tour, liên kết các POI có sẵn vào một lộ trình cụ thể. Hệ thống tự khởi tạo mã QR tĩnh tương ứng cho từng lộ trình phục vụ mục đích in ấn vật lý.

QR Code Auto-generation
🌐

5.4 Đa ngôn ngữ và Bản địa hóa

Cấu trúc lưu trữ động (Dictionary) đối với trường Content và đường dẫn file Audio. Kịch bản Fallback hoạt động nếu tại thời điểm đó bài nghe tiếng Anh chưa được cập nhật, dữ liệu sẽ tự động sử dụng Audio tiếng Việt làm dự phòng.

Dynamic Locale Content
🔉

5.5 Nhận diện vị trí

Tại ứng dụng Client (Mobile), hệ thống sẽ giám sát vị trí thông qua Service GPS. Khi du khách bước vào vùng ranh giới (Radius) của điểm POI, ứng dụng sẽ gửi thông báo mềm (Push Notification) và chủ động phát Audio tương ứng.

Background Location Access
📊

5.6 Tracking & Trích xuất Analytics

Ghi nhận hệ tọa độ theo chu kỳ của khách hàng (lộ trình di chuyển). Biểu diễn theo dạng bản đồ nhiệt (Heatmap) trên Dashboard Admin giúp phân tích xu thế, tối ưu không gian cho các điểm dễ tụ tập đám đông.

6. Mô hình dữ liệu (Data Models - Firestore)

Hệ thống tuân thủ mô hình CSDL phi quan hệ (NoSQL Format) trên nền tảng Firestore. Kiến trúc cụ thể cho các Collection cốt lõi được mô tả dưới đây:

1. Lược đồ Dữ liệu

Thuộc tính Phân loại (Type) Mô tả cấu trúc
Id String (Auto) Khóa chính (Document ID)
Name, Description String Cụm thông tin đặt tên, lưu trữ tham chiếu chung
CoverImageUrl String Tuyến liên kết ảnh giao diện
PoiIds List<String> Mảng tham chiếu ID của các cấu phần POI liên quan
IsActive Boolean Cờ phân trạng thái khả dụng lên hệ thống chung
QrCodeUrl String Tham chiếu kho lưu trữ điểm QR Code khởi tạo
TotalScans Number Biến đếm lưu lượng quét truy cập

2. Lược đồ Dữ liệu Điểm đặc trưng (Poi Collection)

Thuộc tính Phân loại (Type) Mô tả cấu trúc
Id String Khóa chính (Document ID)
Name String Định danh quản trị nội bộ đối với điểm lưu ý
Latitude, Longitude Number (Double) Định vị hệ tọa độ địa lý chuẩn
Radius Number (Double) Tham số phạm vi giới hạn nhận diện (đo theo mét)
DisplayOrder Number (Int) Thứ tự đề xuất trong kiến trúc Tour
Translations Map<String, PoiLangConfig> Bộ dữ liệu Map bản đồ ngôn ngữ truy xuất tĩnh

3. Lược đồ Phân tích

Thuộc tính Phân loại (Type) Mô tả cấu trúc
SessionId String Token phiên giao dịch truy xuất tự động của một user cụ thể
EventType String Cờ sự kiện, bao gồm: "enter_poi", "leave_poi", "play_audio"
TargetId String Định danh đối chiếu lên hệ Tour/POI tương quan
Lat, Lng Number Tọa độ bắt được tại thời điểm (tiêu chuẩn bảo mật làm tròn 3 chữ số thập phân)

7. Yêu cầu phi chức năng (Non-Functional Requirements)

  • 7.1 Yêu cầu Bảo mật, An toàn thông tin (Security Standard):
    • Giao thức API trao đổi phải tuân thủ chuẩn xác thực JWT qua hạ tầng của Firebase.
    • Quy chuẩn kiểm soát quyền truy cập: Admin thao tác đặc quyền đọc/ghi trên mọi Collections, ngược lại phía Client Mobile chỉ kế thừa quyền Đọc (Read-Only) và quyền chèn bổ sung nhật ký vào Analytics Collection (Append-Only Method).
  • 7.2 Bảo vệ quyền riêng tư người dùng đích (Privacy First):
    • Hệ thống vận hành theo quy chuẩn No PII (Không thu thập Thông tin định danh cá nhân) như Tên, SĐT, hoặc MAC Device.
    • Cấu trúc lưu vết GPS tự động làm tròn trị số vào cơ sở dữ liệu làm giảm mức độ chi tiết (sai số xấp xỉ ~111m) - hỗ trợ thiết lập Heatmap mà không vi phạm quy chuẩn riêng tư.
  • 7.3 Tiêu chuẩn Hiệu năng & Khả năng Ngoại tuyến (Performance System):
    • Dữ liệu đệm (Caching Mechanism): Đối với lần khởi chạy thiết lập Tour, ứng dụng đồng bộ hóa văn bản (Text) và file Audio đính kèm và lưu trữ vào phân vùng bộ nhớ cục bộ (SQLite / Local Storage) để duy trì khả năng hồi đáp trong trường hợp thiết bị mất kết nối Internet tĩnh.
    • Độ trễ tiêu chuẩn (Latency) cho các endpoint trích xuất POI đảm bảo <= 300ms.
  • 7.4 Quản trị toàn vẹn hệ thống (Maintainability Scale): Áp dụng cấu trúc Clean Architecture cho khối Backend kết hợp nguyên lý CQRS rút gọn cho phép khả năng mở rộng (Scale-out) riêng biệt tài nguyên đọc tải lưu lượng trên diện rộng ứng dụng phục vụ du lịch.

8. Lộ trình phát triển sản phẩm (Product Roadmap)

Giai đoạn 1: MVP Nền tảng (Tháng 1-2)

  • Triển khai lõi backend C# Web API & Khởi tạo thiết lập Google Firebase.
  • Xây dựng CMS phục vụ Admin thiết lập trực quan hệ thống Tour và POI.
  • Xây dựng Web-App hỗ trợ khách tham quan truy cập và tiếp nhận nội dung đa phương tiện tức thì qua thao tác quét QR (không yêu cầu cài đặt ứng dụng).

Giai đoạn 2: Nâng tầm Trải nghiệm (Tháng 3-4)

  • Đóng gói Ứng dụng gốc phân phối qua các kho tải cho hệ sinh thái di động Native (App Store & Google Play).
  • Kích hoạt tính năng Geo-fencing cảnh báo vùng lân cận điểm POI.
  • Áp dụng luồng Audio phát nền (Background Service) và xây dựng Caching Database duy trì tác vụ ngoại tuyến.

Giai đoạn 3: Phân tích Dữ liệu Lớn (Tháng 5+)

  • Khai thác lượng dữ liệu (Logs) và hiển thị trực quan thông qua Heatmap Dashboard trên nền tảng Admin.
  • Phát triển Hệ thống Gợi ý (Recommend System) đề xuất lộ trình trải nghiệm cá nhân hóa.
  • Mở rộng API hệ thống kết nối với các đối tác xuất vé và phân phối dịch vụ tiện ích khác.
